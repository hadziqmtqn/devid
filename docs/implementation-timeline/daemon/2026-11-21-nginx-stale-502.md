# Fix: a proxy site answers as soon as its dev server starts, not 10 s later

> Date: 2026-11-21 · Branch: `fix/nginx-stale-502` · Phase 10 O2 (`docs/roadmap/phase-10.md`)

## Problem

On nginx, after a proxy site's dev server came up, `https://<site>.test` kept answering "Nothing answers on localhost:<port>" for up to 10 s. Found while spiking Phase 10 (dev servers on demand): with Devid 0.16's exact proxy shape, a server that had just started got 502 for 10.6 s, polled every 0.5 s. A request that wakes a dev server would hit the same wall.

## Cause

- `proxy_pass http://localhost:<up>` makes an implicit upstream group of two addresses, 127.0.0.1 and ::1.
- nginx skips an address that refused for `fail_timeout` (10 s) after `max_fails` (1) failure.
- While a dev server is down, both addresses refuse. For the next 10 s nginx answers "no live upstreams" without trying either, even once the server listens.

## What did not work

`max_fails=0` on both addresses for the main path. nginx then round-robins over both on every request, so a dev server on one address (Vite: ::1 only; most others 127.0.0.1) gets a refused attempt on every other request. Each refusal is a line in nginx's error log: 20 lines for 40 requests, against 1 with the implicit group.

## Fix

- **Main path unchanged:** `location /` still proxies to `localhost:<up>`. That group skips the unused address and keeps the log quiet: 1 line per 10 s, as before.
- **A retry group per proxy site,** `upstream devid_again_<site>`, with `max_fails=0` on `127.0.0.1:<up>` and `[::1]:<up>`.
- **Where a failure goes:** a 502 or 504 now goes to `@devid_again`, which proxies the same request through the retry group with the same headers, and only then to `@devid_down` (today's message). The second `error_page` needs `recursive_error_pages on`.
- **No repeats:** only a request that never reached the dev server goes again.
  - `@devid_again` starts with `if ($upstream_bytes_sent ~ "[1-9]") { return 502; }`, which ends at `@devid_down`.
  - A server that took the request and dropped it (a Next.js restart mid-request) does not get a POST twice.
  - `$upstream_connect_time` could not tell the two apart: a refused loopback connect also records `0.000`.
- **Not changed:** Caddy and Apache. Caddy keeps no failure state unless passive health checks are configured, and Apache's proxy line already has `retry=0`. Neither server was tested for this.

## Checks

On the owner's M1 with nginx 1.30.7, first in a scratch nginx on spare ports:

| Case | 0.16 shape | `max_fails=0` main path | This fix |
|---|---|---|---|
| Right after the server starts | 502 for 10.6 s | 200 | 200 from 0.21 s |
| Error-log lines per 40 requests, server on 127.0.0.1 only | 1 | 20 | 1 |
| Server on ::1 only (like Vite) | 200 | 200 | 200, 1 line per 40 requests |
| Server down | "Nothing answers" | — | "Nothing answers", 4 lines per request |
| Server takes a POST and closes | 502 | — | 502, the POST delivered once |

Then through a real Devid daemon:

- **`scripts/smoke.sh`,** which every release runs on both arches, gains a proxy check:
  - a proxy site on port 28300 says "Nothing answers";
  - a `python3 -m http.server` then starts on 127.0.0.1, and the very next request through `front.test` must get its page;
  - the same again with the server on ::1 only.
- **The new check against both builds:**
  - It passes with this build: PHP, proxy and Mail smoke tests all passed on arm64 in 18 s.
  - It fails with the installed devid 0.16.0: "FAIL: front.test right after its dev server started on 127.0.0.1: Nothing answers on localhost:28300…".
- **Unit tests:** `render_static_and_proxy` checks the retry group, the guard, the headers in `@devid_again` and the main path. `render_local_port` checks that a proxy site with a local port defines one retry group for both of its server blocks.
- **Repository checks:** `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` (117 tests) pass.
