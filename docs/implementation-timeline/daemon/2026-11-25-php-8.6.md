# PHP 8.6 next to 8.3, 8.4 and 8.5 (D-062, v0.20.1)

> Date: 2026-11-25 · Branches: `php-8.6` here and in devid-binaries, and `imagick-libde265` there · PRs: hadziqmtqn/devid-binaries#25 (the builds), hadziqmtqn/devid-binaries#26 (imagick on Linux), #147 (0.20.1), hadziqmtqn/devid-site#21 (the guide) · Releases: runtime `2026.11.25-22`, `devid-v0.20.1` (Latest)

## Problem

php.net released PHP 8.6.0 on 2026-11-19, and the owner asked whether Devid should add it. static-php-cli 2.8.5, which builds every Devid PHP, predates 8.6, and so do the stable Xdebug, pcov and phpredis. D-062 records the owner's answers.

## Change

- **devid-binaries (#25, and #26 after the first release run):**
  - **The PHP build, 8.6 only:** Xdebug 3.6.0alpha1 from its GitHub tag, phpredis 6.4.0RC1, and pcov from its fix commit `c96a5742`, through spc's `--custom-url`. spc's PHP configure command gets the two fixes spc's v3 branch makes: `--enable-pic` instead of `--with-pic` (Linux), and `CXXFLAGS` that include `<locale>` before `php.h`, whose `vsnprintf` macro breaks libc++'s `<locale>` in ext/intl. CI turned up two more:
    - spc applies phpmicro's patches in their newest version up to the PHP version, and its list ends at 8.5, so for 8.6 it took the 8.0 patches, which do not apply. 8.6 names the ones 8.5 resolves to (`disable_huge_page_84`, `macos_iconv_84`).
    - On Linux, 8.6's new poll API calls `epoll_pwait2` when configure finds a declaration, and zig's glibc headers have one, but glibc 2.17 has no such symbol. `ac_cv_func_epoll_pwait2=no ac_cv_have_decl_epoll_pwait2=no` make it use `epoll_wait`.
  - **Every version:** `build-php.sh` checks that `pcov.so` loads in php and php-fpm, and `BUILDINFO` records the Xdebug, pcov and phpredis versions that were built.
  - **The catalog for 8.6:** imagick, ldap and mongodb. `extensions/php-8.6-compat.h` gives 8.6 builds back the aliases 8.6 removed, with their 8.5 definitions; imagick 3.8.1 needs them. apcu, igbinary, memcached, msgpack and swoole set `SKIP` for 8.6, so `build-ext.sh` builds nothing for them and the manifest has no 8.6 entry.
  - **imagick on Linux (#26):** libde265 is built without its AVX2 and AVX-512 kernels, which zig cannot link (see "The Linux imagick failure").
- **The daemon:** `php::SUPPORTED` lists 8.6, and `install::SHIMS` adds `php8.6`, so `devid setup` links it in `~/.devid/bin` next to the other commands (D-053). `devid self-update` runs the new binary's setup, which links it on existing installs. `default_php` stays 8.5 for new installs.
- **The CLI and the TUI:** `devid php install 8.6`, `devid isolate 8.6` and `devid setup --php 8.6` accept it. The PHP page has four rows. Its menu title took the version from `SUPPORTED[row.min(2)]`, which would have named 8.5 on the 8.6 row; it now clamps to the list's length.
- **The app:** `SUPPORTED_PHP` lists 8.6, so the PHP page shows a fourth row with Install.
- **`scripts/smoke.sh`:** after the existing checks, each release installs 8.6 from `runtime-latest`, pins the test site to it, turns Xdebug and pcov on through Devid, and expects the site to answer `smoke 8.6.<patch> xdebug,pcov` over HTTPS.
- **Docs:** D-062, D-009's amendment, the README, CONTRIBUTING, CLAUDE.md (with the owner's OK), PROJECT_CONTEXT and ARCHITECTURE.

### The Linux imagick failure

- **What failed:** ImageMagick's `utilities/magick` did not link: `undefined symbol: __cpu_indicator_init` and `__cpu_model`, from libde265's `x86/sse.cc`.
- **Why:** libde265 1.1 (June 2026) picks its AVX2 and AVX-512 kernels with `__builtin_cpu_supports`, which reads a CPU table from libgcc or compiler-rt. zig 0.17.1's runtime has no such table. On macOS, clang links compiler-rt, which has it, so both darwin jobs passed.
- **Why #25's CI passed:** it built the same recipe for 8.6 on Linux from a cold cache, with the same zig, libde265 1.1.3 and libheif 1.23.7, and its libde265 had no AVX2 dispatch. Why configure turned AVX2 on in the release job is not in the logs, because spc keeps its library logs on the runner. The cached 8.3 to 8.5 build roots also hold a libde265 without the dispatch.
- **The fix (#26):** on Linux, when the build root has no `libde265.a`, `extensions/imagick.sh` has spc download and extract libde265, sets `ENABLE_AVX2` and `ENABLE_AVX512` to `OFF` in its `CMakeLists.txt`, and lets `spc build:libs` build from that source. The SSE4.1 kernels check the CPU with `cpuid` and stay. static-php-cli's v3 branch turns all of libde265's SIMD off for the same error.

## Follow-ups

- **The M1:** `devid self-update` to 0.20.1 and PHP 8.6 on the owner's M1 (`php8.6`, a site pinned to 8.6 over HTTPS) wait for the owner's OK.
- **The guide:** hadziqmtqn/devid-site#21 is ready to merge.

- **The default:** 8.6 becomes the default in a release of its own once Xdebug 3.6.0 is stable and the catalog builds for 8.6 (D-062).
- **The 8.6 pins:** drop Xdebug 3.6.0alpha1, phpredis 6.4.0RC1 and the pcov commit as their projects release 8.6 support, and the configure fixes once static-php-cli releases its own.
- **The catalog:** apcu, igbinary, memcached, msgpack and swoole build for 8.6 once a release of theirs supports it; remove the recipe's `SKIP` then. The weekly catalog report lists their new releases.
- **libde265's AVX2:** turn it back on if zig's runtime gains the CPU table, or if libde265 checks the CPU without `__builtin_cpu_supports`. Until then, the recipe fails with its own message if a libde265 still calls the builtin but drops either option.
- **Logs:** devid-binaries' workflows could upload spc's library logs when a job fails, so a configure step's choices can be read afterwards (not decided).
